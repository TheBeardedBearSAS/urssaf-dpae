# Doctrine persistence

The Doctrine bridge (`TheBeardedBear\UrssafDpae\Bridge\Doctrine`) persists the deposits, the tracked returns, the
downloaded documents, the synchronisation cursors and the outbox with Doctrine ORM 3 / DBAL 4. It is optional:
`doctrine/orm`, `doctrine/dbal` and `doctrine/doctrine-bundle` are `require-dev` and `suggest` entries, with a `conflict`
floor (`doctrine/orm < 3.5.3`, `doctrine/dbal < 4.0`, `doctrine/doctrine-bundle < 2.19`). Without it the in-memory
repositories remain, for tests and trials: the full lifecycle (atomic claim, unknown outcome, reconciliation, return
synchronisation and download, [ADR 0005](adr/0005-deposit-result-and-unknown-outcome.md),
[ADR 0006](adr/0006-polling-constraints.md)) needs durable repositories ([ADR 0008](adr/0008-doctrine-persistence.md)).

The domain classes carry no Doctrine metadata. The mapping is a set of XML files in
`src/Bridge/Doctrine/Resources/mapping`, one per table, that map **row entities** (`Bridge\Doctrine\Entity\*Record`,
`OutboxMessage`). The ORM is used for the schema (`doctrine:migrations:diff`, the schema tool), never for the unit of
work: the repositories read and write the tables with DBAL on the connection of the entity manager, which is what makes the
optimistic lock and the claim plain conditional statements, and what keeps the entity manager open when a save loses a race
(an ORM flush that fails closes the entity manager). The row entities are not declared `final`, nor `readonly`, so that
Doctrine can generate their proxies with any `auto_generate_proxy_classes` mode (including the pre-generation of the cache
warm-up: a proxy cannot extend a readonly class before PHP 8.3); they are final by convention (`@final`) and must not be
extended. The identifier of each is neither readonly nor private, because Doctrine assigns it again when a proxy is loaded.

## Tables

Every table, index, constraint and DBAL type is prefixed with `urssaf_dpae_` (`DoctrineIntegration::TABLE_PREFIX`,
[ADR 0009](adr/0009-coexistence.md)): indexes are `idx_urssaf_dpae_*` and `uniq_urssaf_dpae_*`, so nothing collides with
the tables of the other URSSAF packages (`urssaf_tps_*`, ...) in the same database. A test enforces it.

### `urssaf_dpae_deposits` (`DepositRecord`)

| Column | Content |
|---|---|
| `id` (PK, 64) | `DepositId`, generated by the package |
| `tenant_id` (64) | `TenantId` |
| `external_reference` (100), `fingerprint` (64) | the reference of the host and the SHA-256 of the flow |
| `mode` (16), `state` (32) | `DeclarationMode`, `DepositState` (`pending`, `depositing`, `received`, `rejected`, `failed`, `invalid_credentials`, `outcome_unknown`, `not_received`) |
| `declarant_siret` (14, null) | the tenant's SIRET for a direct identity |
| `attempts`, `claimed_at`, `updated_at` | attempts claimed, the last claim (origin of the reconciliation window), the last change |
| `flow_id` (50, null) | `IdFluxDPAE`, once known (receipt, or reconciliation) |
| `result` (text, null) | the answer of URSSAF as a JSON document: kind (`receipt` / `rejection`), flow id, declarant SIRET, generation instant, reject reasons, content type and raw document in base 64 |
| `last_error_code` (100, null) | stable `deposit.*` code of the last problem |
| `adopted` | whether the reconciliation inferred the flow id |
| `version` | the optimistic lock version |
| `open_reference`, `open_fingerprint` (null) | the reference and the fingerprint while the deposit is open, `NULL` once it is `failed`, `rejected` or `not_received` |

Constraints and indexes: unique `(tenant_id, flow_id)`, unique `(tenant_id, open_reference)`, unique
`(tenant_id, open_fingerprint)` (a portable partial uniqueness: an open deposit is unique per tenant on its reference and
on its flow, [ADR 0005](adr/0005-deposit-result-and-unknown-outcome.md); `NULL`s are distinct on every supported platform
but SQL Server), index `(tenant_id, state, claimed_at)` for `withoutFlowId()` and `staleDepositing()`, `(tenant_id, state,
updated_at)` and `(tenant_id, external_reference)`.

**Collation.** The uniqueness of the open reference and of the flow id, and the lookups by reference, compare strings with
the collation of the column. A case-insensitive or accent-insensitive collation (the MySQL/MariaDB default,
`utf8mb4_0900_ai_ci`, `utf8mb4_unicode_ci`, or SQL Server's) makes `REF-1` and `ref-1` the same reference and `flow-a` and
`FLOW-A` the same flow id for the unique indexes, whereas the domain, URSSAF and the in-memory repositories treat them as
different values. Give `external_reference`, `open_reference`, `flow_id` (and `return_id`, `flow_id` of the returns) a
**binary collation**: `utf8mb4_bin` on MySQL/MariaDB, `"C"` (or `ucs_basic`) on PostgreSQL, `BINARY` on SQLite (its default),
`Latin1_General_BIN2` on SQL Server. The mapping cannot fix it for every platform, so set it in your migration after
`doctrine:migrations:diff` (`ALTER TABLE urssaf_dpae_deposits MODIFY open_reference VARCHAR(100) CHARACTER SET utf8mb4 COLLATE
utf8mb4_bin NULL`, the same for the other columns), or declare it on a schema listener with the column option `collation`.
Without it the failure is on the safe side (a false `deposit.reference_conflict`), never a duplicate.

### `urssaf_dpae_returns` (`ReturnRecord`)

One row per `(tenant, flux.id, nature, ops)` ([ADR 0006](adr/0006-polling-constraints.md)). The aggregate has no
identifier: the primary key `id` is the SHA-256 of the identity (`ReturnRecord::key()`), so that the same return found
by another listing is the same row. Columns: `tenant_id`, `flow_id`, `nature` (the raw code), `has_ops` and `ops`
(see below), `status` (the raw `statut`), `publication_raw` / `publication_at`, `production_raw` / `production_at` (the
raw strings and their parsed instants, null when unparsable), `return_id` (`retour.id`, null), `delegate`, `url`,
`deposit_id` (null), `download_state` (`pending`, `downloaded`, `not_downloadable`, `purged`), `first_seen_at`, `updated_at`.
Unique `(tenant_id, flow_id, nature, has_ops, ops)`; indexes `(tenant_id, publication_at)`,
`(tenant_id, download_state, publication_at)` and `(tenant_id, first_seen_at)`.

### Other tables

- `urssaf_dpae_return_contents` (`ReturnContentRecord`): `return_id` (PK, the key of the return, no foreign key: the content
  is stored before the return), `tenant_id`, `content_type`, `content` (base 64 text), `size`, `sha256`, `downloaded_at`
  (the clock of the package when it was stored). Index `(tenant_id, downloaded_at)`.
- `urssaf_dpae_sync_cursors` (`SyncCursorRecord`): `tenant_id` (PK), `cursor_at`, `last_success_at`,
  `consecutive_refusals`.
- `urssaf_dpae_outbox` (`OutboxMessage`): the integration events (`urssaf.dpae.*`) relayed at least once, in append order
  (`sequence`), written with DBAL in the transaction of the state change. Unique `event_id`.
- `urssaf_dpae_deposit_flows` (`DepositFlowRecord`): `deposit_id` (PK), `flow` (gzip, then base 64).

DBAL types (`DoctrineIntegration::types()`): `urssaf_dpae_tenant_id`, `urssaf_dpae_deposit_id`,
`urssaf_dpae_external_reference`, `urssaf_dpae_flow_id`, `urssaf_dpae_fingerprint`, `urssaf_dpae_siret`,
`urssaf_dpae_instant` (always UTC, whatever the time zone of the process), `urssaf_dpae_deposit_result`,
`urssaf_dpae_bytes` (base 64 in a text column: the same string on every platform, no BLOB stream, no character set
between the bytes of an ISO-8859-1 document and the database).

### Differences from the table of ADR 0008

- `nature` and `statut` are stored raw only; the parsed values (`ReturnReference::nature()`, `status()`) are derived from
  them by the domain, never stored twice.
- An absent `ops` differs from an empty one in the port (and in memory), but the unique index must not see a `NULL`: the
  row has a `has_ops` flag, and `ops` is `''` when absent. The ADR's single non-null `ops` column would merge the two.
- The answer of URSSAF is one `result` column (kind, flow id, SIRET, instant, reasons, document) instead of a kind and a
  document column; the aggregate has no size, so there is no `size` column on the deposit; `adopted` is added (the
  aggregate records it).
- `urssaf_dpae_returns` has a derived `id` and `urssaf_dpae_return_contents` is keyed by it; the cursor column is
  `cursor_at`; three more indexes serve the queries above.
- The columns equal to the external reference and the fingerprint while the deposit is open are `open_reference` and
  `open_fingerprint`, as the ADR describes.
- The mode and the states are plain string columns mapped with `enum-type`: there is no `urssaf_dpae_declaration_mode` type
  (the ADR lists it among the examples), the nine types of `DoctrineIntegration::types()` are the ones the columns need.

## Registering types and mapping without Symfony

```php
use TheBeardedBear\UrssafDpae\Bridge\Doctrine\DoctrineIntegration;

DoctrineIntegration::registerTypes();                                          // idempotent, global DBAL type registry
$configuration->setMetadataDriverImpl(DoctrineIntegration::mappingDriver());   // SimplifiedXmlDriver
```

`DoctrineIntegration::types()` returns the custom types by name, `mappingDirectory()` the XML directory,
`MAPPING_NAMESPACE` the namespace prefix handled by the simplified driver, and `doctrineBundleConfiguration()` the array
the Symfony bundle prepends to the `doctrine` extension (types and mapping of the default entity manager, or of the one
you name, `doctrineBundleConfigurationFor('urssaf')` / `doctrineBundleConfigurationForWith('urssaf', $ormOptions)`, plus the native
lazy objects when PHP 8.4 and the ORM support them: `symfony/var-exporter` 8 dropped the lazy ghosts the ORM proxy factory
relies on; without the Symfony bundle, `$configuration->enableNativeLazyObjects(true)` when
`DoctrineIntegration::nativeLazyObjectsAvailable()`).

Then build the persistence from your `EntityManagerInterface` and hand it to the builder:

```php
use TheBeardedBear\UrssafDpae\Standalone\Persistence;

$persistence = new Persistence(
    new DoctrineDepositRepository($entityManager),
    new DoctrineReturnRepository($entityManager),
    new DoctrineSyncCursorRepository($entityManager),
    new DoctrineReturnContentStore($entityManager, $clock),   // $clock: Application\Port\Clock, e.g. Infrastructure\Clock\SystemClock
    new DoctrineOutbox($entityManager),
    new DoctrineTransactionManager($entityManager),
);
$dpae = UrssafDpaeBuilder::create($transport, $credentials, $configuration)->withPersistence($persistence)->build();
```

The repositories, the content store and the outbox must share the connection of the transaction manager (they do when
they are built from the same entity manager): the outbox rows and the state change are written in one transaction.

## Dedicated entity manager (recommended)

The repositories never `persist()` nor `flush()` and never touch the unit of work, so they do not flush half-finished
entities of your application. Statements run on the connection of the entity manager, though, and
`DoctrineTransactionManager` wraps them in a transaction of that connection: a statement of your own on the same
connection inside a handler would join (and be rolled back with) the package transaction. Use a **dedicated connection
and entity manager** for the package tables, and point the bundle at it (the same database is fine):

```yaml
doctrine:
    dbal:
        connections:
            default: { url: '%env(resolve:DATABASE_URL)%' }
            urssaf:  { url: '%env(resolve:URSSAF_DATABASE_URL)%' }
    orm:
        entity_managers:
            default: { connection: default, mappings: { App: { type: attribute, dir: '%kernel.project_dir%/src/Entity', prefix: App\Entity } } }
            urssaf:
                connection: urssaf
                mappings:                                             # the package mapping, on this entity manager only
                    UrssafDpae:
                        type: xml
                        is_bundle: false
                        dir: '%kernel.project_dir%/vendor/thebeardedbear/urssaf-dpae/src/Bridge/Doctrine/Resources/mapping'
                        prefix: 'TheBeardedBear\UrssafDpae'
                        alias: UrssafDpae
```

A package that prepends `DoctrineIntegration::doctrineBundleConfigurationFor('urssaf')` to the `doctrine` extension (the
bundle of the next lot does) writes the same `orm.entity_managers.urssaf.mappings` entry for you; without a name the mapping
goes to the default entity manager, which then also maps the tables of the package.

## Transactions

`DoctrineTransactionManager::transactional()` runs the operation in a DBAL transaction: it commits when the operation
returns and rolls back, rethrowing the same throwable, when it throws. Nested calls (and a call inside a transaction of
your application) open a **savepoint** on platforms that support them: a failing inner operation is undone to its
savepoint, and everything becomes durable only when the outermost transaction commits. The domain events are published by
`UnitOfWork` right after the operation returns, so inside an outer transaction of yours before its commit: rely on the
outbox, written in the same transaction, for what must not be lost.

## Concurrency

- **Optimistic lock.** `save()` inserts the first version of a deposit (`version` 1) and afterwards runs
  `UPDATE ... WHERE id = :id AND version = :read` with `version = :read + 1`. No row updated is
  `Domain\Exception\ConcurrentModification` (`deposit.concurrent_modification`); the aggregate is then discarded and the
  caller reads it again (`Application\Service\DepositUpdater` does, three attempts). A copy read before another save or
  before a claim can never overwrite it. The entity manager stays open.
- **Claim.** `claim($id, $now, $maxAttempts)` is one
  `UPDATE ... SET state = 'depositing', attempts = attempts + 1, claimed_at = :now, updated_at = :now, version = version + 1
  WHERE id = :id AND state = 'pending' AND attempts < :max`: exactly one worker wins (`true`), the others get `false`. It
  loads nothing: call `get()` again to read the claimed deposit. An unknown id is `RecordNotFound`, as in memory.
- **Queries.** `withoutFlowId()` and `staleDepositing()` order by `claimed_at` (oldest claim first), then `id`, and limit in
  the query.
- **Uniqueness.** The statement of a save runs in its own (nested) transaction, a savepoint inside the transaction of the
  unit of work: a refused statement aborts the transaction on some platforms, and the rows must be readable to explain it.
  A unique violation on a save is explained by reading the rows: another open deposit of the tenant with
  the reference is `deposit.reference_conflict`, with the fingerprint `deposit.flow_already_open` (the codes the handler
  uses before it saves; the constraint is the safety net against concurrent inserts), the id or the flow id already stored
  is `deposit.concurrent_modification` (reload and decide again). The reference held by an open deposit **with the same
  fingerprint** is the same deposit asked twice at once, not another flow: it is `deposit.concurrent_modification` too
  (retryable: the reload finds the deposit by its reference), only a different fingerprint is `deposit.reference_conflict`.
  A violation nothing explains is rethrown as the driver's `UniqueConstraintViolationException`.
- **MySQL/MariaDB `REPEATABLE READ`.** The rows that explain a refusal are read in the transaction that was refused: under
  `REPEATABLE READ` (the InnoDB default) that transaction keeps its snapshot, which cannot see the row another transaction
  committed after it began, so nothing explains the violation and the driver's raw `UniqueConstraintViolationException` is
  rethrown instead of the domain code. The savepoint of the statement is rolled back and the entity manager stays open: treat
  that exception as retryable (reload, decide again), or run the transactions of the package in `READ COMMITTED`
  (`SET SESSION transaction_isolation = 'READ-COMMITTED'` on the dedicated connection), where the codes above are exact.
  PostgreSQL (`READ COMMITTED` by default) and SQLite are not concerned.
- **Returns, contents and cursors** are saved by key (a row is updated when it exists, inserted otherwise): they have no
  version, and a second writer inserting the same key at the same instant gets the driver's unique violation, which the
  next run of the synchronisation does not meet again.
- **A download is not overwritten by a synchronisation.** A listing that read a return before its download finished still
  holds a `pending` copy. `DoctrineReturnRepository::save()` of a copy that is not `downloaded` is
  `UPDATE ... WHERE id = :id AND NOT (download_state = 'downloaded')`: it leaves a `downloaded` row as it is (the listing of
  that run is dropped, the next synchronisation lists it again), so the stored document is never orphaned. The save of a
  `downloaded` copy is unconditional. `purged` and `not_downloadable` are not protected: they are not final for the
  listing (`not_downloadable` goes back to `pending` when the return gains a document).

## Kept flows

The flow is the most sensitive data of the package and the fingerprint plus the result document are enough to reconcile:
the package keeps no flow by itself. A host that must keep an exact copy (`persistence.keep_flows`, the Symfony bundle
option of the next lot) calls `DoctrineDepositFlowStore::keep($depositId, $flow)` and reads it with `find($depositId)`
(gzip, base 64). Nothing in the package calls it. `delete($depositId): bool` erases the kept flow alone (see "Erasure").

## Personal data (GDPR)

The flows and the returns carry personal data of the employees (NIR, name, birth data, address) and of the employer. The
package gives you the tools, the policy is yours, and the specification publishes no retention period for the copy of the
host ([ADR 0008](adr/0008-doctrine-persistence.md)):

| Table | Personal data |
|---|---|
| `urssaf_dpae_deposits` | `result`: the receipt (AEE) or the rejection notice, as URSSAF answered it |
| `urssaf_dpae_deposit_flows` | the deposited flow itself (only if you keep flows) |
| `urssaf_dpae_return_contents` | the downloaded documents (AEE, conformity certificate, anomaly report) |
| `urssaf_dpae_returns` | the identifiers of the flux and of the declarant (`delegate`), no employee data |
| `urssaf_dpae_outbox` | integration events: identifiers and references only, never the personal data |

1. **Retention.** Returns are available at URSSAF for **3 months**, then purged (a later download is a 404), and the
   follow-up data stay in the consultation service for **13 months**. `urssaf_dpae_returns` and
   `urssaf_dpae_return_contents` are **kept beyond the URSSAF purge**, which is the purpose of the bridge; the package
   defines **no local retention period** and deletes nothing on its own. Define yours and run a scheduled job that calls:
   - `DoctrineReturnContentStore::deleteDownloadedBefore(TenantId, Instant): int`: the documents stored before the instant
     (the return stays);
   - `DoctrineReturnRepository::deleteSeenBefore(TenantId, Instant): int`: the returns first seen before the instant and
     their contents;
   - `DoctrineDepositRepository::deleteFinishedBefore(TenantId, Instant): int`: the deposits that reached a final answer
     (`received`, `rejected`, `failed`, `not_received`) and were last updated before the instant, with their kept flow. A
     deposit that is forgotten no longer guards its reference and its flow against a second deposit;
   - `Outbox::purgeDispatchedBefore(Instant)`: the events already relayed.

   **Orphan link.** `urssaf_dpae_returns.deposit_id` has no foreign key: after `deleteFinishedBefore()` a return keeps the id
   of a deposit that no longer exists. That is intended (the return is kept beyond the deposit, and the link is only the
   shared `flux.id`); do not follow `deposit_id` without handling "no row", and use `flow_id` to find the deposit, if it
   is still stored.
2. **Erasure** (right to erasure of one person or one declaration, no domain event, nothing at URSSAF: the data there follows
   its own retention rules) deletes by key, whatever the state:
   - `DoctrineDepositRepository::delete(DepositId): bool` and
     `DoctrineDepositRepository::deleteByReference(TenantId, ExternalReference): int` (one per past attempt) delete the
     deposits and their kept flows, in one transaction:
     `DELETE FROM urssaf_dpae_deposit_flows WHERE deposit_id IN (SELECT id FROM urssaf_dpae_deposits WHERE tenant_id = :tenant AND external_reference = :ref)`
     then `DELETE FROM urssaf_dpae_deposits WHERE tenant_id = :tenant AND external_reference = :ref`;
   - `DoctrineDepositFlowStore::delete(DepositId): bool` keeps the deposit and erases its flow
     (`DELETE FROM urssaf_dpae_deposit_flows WHERE deposit_id = :id`);
   - the documents and returns of the same declaration are keyed by flow, not by deposit: read the flow id of the deposit
     first (`flow_id`, null if it never got one), then
     `DELETE FROM urssaf_dpae_return_contents WHERE return_id IN (SELECT id FROM urssaf_dpae_returns WHERE tenant_id = :tenant AND flow_id = :flow)`
     and `DELETE FROM urssaf_dpae_returns WHERE tenant_id = :tenant AND flow_id = :flow`, on the connection of the entity
     manager, in one transaction (`DoctrineTransactionManager`). The `outbox` rows hold no personal data.
   - Erasing a deposit frees its reference and its fingerprint: a new deposit under the same reference is accepted.
3. **Encryption at rest.** `result`, `content` and `flow` go through the types `urssaf_dpae_deposit_result` and
   `urssaf_dpae_bytes`, registered under stable names. The types are `final`: to encrypt a column, write a type of your own
   that wraps the package one and register it under the same name, after `DoctrineIntegration::registerTypes()`:

   ```php
   final class EncryptedBytesType extends Type
   {
       public function getSQLDeclaration(array $column, AbstractPlatform $platform): string
       {
           return $platform->getClobTypeDeclarationSQL($column);
       }

       public function convertToDatabaseValue(mixed $value, AbstractPlatform $platform): ?string
       {
           // the package type base-64 encodes the bytes: encrypt the bytes first, then let it encode the ciphertext
           return (new BytesType())->convertToDatabaseValue($value === null ? null : $this->cipher()->encrypt($value), $platform);
       }

       public function convertToPHPValue(mixed $value, AbstractPlatform $platform): ?string
       {
           $cipher = (new BytesType())->convertToPHPValue($value, $platform);

           return $cipher === null ? null : $this->cipher()->decrypt($cipher);
       }
   }

   Type::overrideType(BytesType::NAME, EncryptedBytesType::class);
   ```

   In Symfony, `DoctrineIntegration::doctrineBundleConfiguration()` registers the type under its name, so override the
   name in **your** configuration, which takes precedence over the prepended one:

   ```yaml
   doctrine:
       dbal:
           types:
               urssaf_dpae_bytes: App\Doctrine\EncryptedBytesType
   ```

   Use authenticated encryption with a key kept outside the database (KMS, Symfony secrets). An encrypted column can no
   longer be searched, which is fine: none of them is queried (the keys are the identifiers, the reference and the
   fingerprint, which are not personal data), but `size` and `sha256` of a stored document describe the clear text, and so does the **fingerprint** of a deposit
   (`fingerprint`, `open_fingerprint`): the SHA-256 of the flow is not the flow, but it is **pseudonymised** data, not
   anonymous: whoever holds a candidate flow can check it against the column (and a flow with little entropy can be
   guessed). Treat it as personal data for access and retention, even if it is not encrypted.
4. **Access, backups and logs.** Restrict who reads the tables above; backups keep what was erased afterwards, so bound
   their retention and replay the erasures after a restore. The package never logs personal data and the value objects mask
   it in `var_dump()`.

## Migrations

The package ships **no migration**: the schema depends on your platform and on the rest of your schema. Generate it in
your application:

```bash
php bin/console doctrine:migrations:diff
php bin/console doctrine:migrations:migrate
```

(or `doctrine:schema:update --dump-sql` for a quick look). Re-run `diff` after each upgrade of the package: the mapping may
evolve (see the changelog). The functional tests run on SQLite (in memory) only. The statements are standard SQL through
DBAL (no `ON CONFLICT`, no `RETURNING`) and the unique indexes never rely on a partial index, so no platform-specific
syntax is expected, but "portable" is a design goal, not a tested guarantee: MySQL/MariaDB, PostgreSQL and SQL Server
differ on the collation of the unique columns (see "Collation") and on the isolation level (see "Concurrency"), and
SQL Server treats `NULL`s as equal in a unique index. Run the contract tests of your repositories on your platform
before production.
